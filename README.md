# 工作记录

工作日志仓库。按「月 → 天 → 任务」三级目录组织，一项任务一个 job 文件，跨天任务通过链接承接成任务链。

**核心原则：job 是索引，不是全文。** 细节不写在 job 里，而是**折叠**到可以按需展开的地方：
代码改动折叠进工程仓库的 commit（用 hash 追溯），大块清单/数据折叠进二级文件（当日的 `file/`），
截图日志折叠进 `temp/`。job 正文只留**结论、指针、待办**——读一遍就能掌握全局，要深挖时再逐层展开。

## 目录结构

```
work_record/                    # 仅保存核心工作记录信息（git 管理）
├── _template/                  # 记录模板（新建时复制去用）
│   ├── job模板.md              #   一级：job 记录（精简）
│   ├── 二级文件模板.md          #   二级：细节展开文档
│   └── todo模板.md
├── _legacy/                    # 历史旧格式记录归档
├── 202609/                     # 按月建目录：YYYYMM
│   ├── 20260901/               # 按天建目录：YYYYMMDD
│   │   ├── job1.md             # 一个 job 文件（按本人指令新建，可含多次需求）
│   │   ├── job2.md
│   │   ├── todo.md             # （可选）当日/长期待办清单
│   │   └── file/               # job 索引出来的细节载体（入 git）
│   │        ├── job2-验证数据.md #   二级文件：文字型细节 / 数据（常规操作）
│   │        ── 20260901_shot.png #  附件：截图等，本人要求保留的才放
│   └── 20260911/
temp/                           # 临时文件（已 gitignore，不入 git）
└── 202609/
    └── 20260911/               # 与 work_record 同构的日期目录
```

## 记录粒度：只按本人指令新建 job

- **唯一的判定标准：本人明确说「新建一个 job」**。收到该指令才建下一个 `jobN.md`。
- 没收到指令时——修 bug、加功能、出下一版、补验证，乃至**另一条新需求**——**一律追加/合并进当前 job 文件**
  （用 `## 追加（M/D HH:MM）：…` 或需求小节）。**不要自己判断「这是另一件事」就开新 job**。
- 所以**一个 job 可以包含多次需求开发、多轮迭代**：粒度跟本人的节奏走，不跟任务类型走。
- **跨天也不新建**：新的一天继续往同一个 job 追加，追加小节里写清日期（`## 追加（9/17 10:30）：…`）。
- 拿不准时**问一句**，不要自行切分粒度；本人说新建，才新建。
- 一天可能有多个 job（本人一天内多次下达新建指令），按 `job1.md`、`job2.md`… 顺序编号
  （编号只由 `jobN.md` 占用，`file/` 里的文件不参与编号）。
- **承接链接块**：仅当本人要求新建 job、且这次工作与其前序工作有承接关系时写，开头用相对链接指向前一个 job
  （任务链靠它串起来）：

  ```markdown
  > [接 9/10 job3 — 写作样本-g 逐年级验收（五年级续）](../20260910/job3.md)
  ```

## 精简与折叠（最重要的一节）

job 会被反复读取，臃肿就是持续的成本。**能靠展开拿到的东西，绝不在 job 正文里重复一遍。**

### 三级折叠

| 级别 | 展开方式 | 放什么 |
|---|---|---|
| **L1 commit** | `git show <hash>` | 代码/配置/文档的具体改动（工程仓库） |
| **L2 二级文件** | 打开当日 `file/<jobN>-<主题>.md` | 大块清单、实测数据表、根因长分析、逐条验证明细 |
| **L3 temp** | 打开文件路径 | 截图、录屏、日志导出、临时脚本、中间数据 |

### job 里**必须**留（完整性底线）

1. 目标 / 需求要点（一行一条，保留本人原话的关键点）
2. 结论与决策，以及**为什么**这么定
3. **每个改动点的 commit hash**；确实没提交的改动，必须自己用文字简述（不能用指针代替）
4. 验证结果的关键数字（通过/失败数、关键实测值）与验证口径（跑的是什么、怎么跑的）
5. 影响面、风险、副作用
6. 遗留待办、待验收项
7. 关键词行（供日后全文检索）

### job 里**不写**（改成指针）

| 不写 | 折叠到 |
|---|---|
| diff、代码片段、逐行函数说明 | commit hash（`git show <hash>`） |
| 大段日志/报错原文 | 正文只留 1 行关键原文，全文进 `temp/` |
| 测试用例逐条清单、逐条断言 | `file/` 二级文件或测试文件本身（写路径） |
| 实测数据大表、枚举清单 | `file/` 二级文件（或导出的数据文件） |
| 「先试 A 不行、再试 B 也不行」的试错流水 | 压缩成一句：试过 A（不行）→ 结论 B |
| 用过即删的探针、临时脚本 | 一行说明，并注明是否已确认无残留 |
| 大段环境/版本罗列 | 只留影响结论的那几项 |

### 量化预算

- **单次推进**（一次开工 / 一次追加小节）正文 ≤ **80 行**。
- **单个 job 文件累计 > 200 行**：把细节抽到当日 `file/`，正文只留摘要 + 链接。
  一个 job 可能包含多次需求开发，累计变大是正常的——**每次追加仍按 ≤ 80 行控制**，靠折叠而不是靠新建文件来控制体量。
- **触发二级文件的阈值**（满足其一且值得日后追溯）：内容 > 30 行、表格 > 6 行、属于「可枚举清单」
  （测试清单、字段清单、实测矩阵、验收清单）。

## 二级文件（放在当日的 file/ 里）

job 保持精简的代价是「细节在 job 外面」，二级文件就是把细节**留在库里**（而不是留在聊天记录里）的容器。
**二级文件与附件统一放在当日的 `file/` 目录**——反正都是被 job 索引出来的，不再另开文件夹。

- **路径**：`work_record/YYYYMM/YYYYMMDD/file/<jobN>-<主题>.md`，如 `file/job2-验证数据.md`；
  同一天同一 job 可以有多份，主题用中文短语。**文件名一律带 `jobN-` 前缀**，方便和 job 对号入座。
  （数据量大时也可以是 `job2-实测矩阵.csv` 等数据文件，同样带前缀。）
  日期目录取**写入当天**——job 跨天时，后续每天的二级文件就放当天目录，job 里用相对路径链接（如 `../20260917/file/job3-xxx.md`）。
- **头部写清**：关联哪个 job（相对链接）、来源 commit 区间、这份文件要留住什么。
- **入 git**：与对应 job 在**同一次提交**里一起提交，不要留在工作区。
- **job 正文引用格式**：

  ```markdown
  > 明细见 [file/job2-验证数据.md](file/job2-验证数据.md)
  ```

- 二级文件是**折叠容器，不是垃圾桶**：只放值得日后追溯的展开内容，不写流水账、不重复 job 已有的结论。
- 模板见 `_template/二级文件模板.md`。
- 与截图的区别：**文字型细节/数据是常规操作，直接写进 `file/`**；截图、录屏、大体积日志仍默认进 `temp/`
  （不入 git），只有本人要求保留时才整理进 `file/`。

## job 自检清单（提交前过一遍）

- [ ] 每个改动点都能找到 commit hash？没提交的改动是否已用文字简述？
- [ ] 正文里任意删掉一段，结论是否仍然完整？——能删的，说明它本该被折叠
- [ ] 还有 > 6 行的表 / > 30 行的清单留在正文吗？→ 移入当日 `file/`
- [ ] 结论、决策理由、验证数字、影响面、遗留待办、待验收、关键词是否齐全？
- [ ] 记录库自己的 commit message 是否一行写完：`记录 <日期> <jobN>：<一句话结果>` + 工程 commit hash？
      （commit message 也会被 `git log --oneline` 读，塞细节等于换个地方臃肿）

## job 文件结构（自上而下）

1. **标题**：`# 任务名 — 本次具体动作`。动作写具体，如「续推进」「提测」「根因排查」「逐年级验收」。
2. **关键词行**：`**关键词**: a, b, c`。列出检索用的项目名/模块名/术语。
3. **设备行**：`**设备**: 设备标识`（见「多设备记录」）。
4. **承接链接块**（本人要求新建 job 且与前序工作有承接关系时必写）：`>` 引用块列出任务链上的前序 job 及相关 job，注明关系（主线/源头/相关）与上次停留的 commit。
5. **状态**：checkbox 进度清单，**边做边勾**（代替流水账）；附本次代码 commit 与是否已推。
6. **目标 / 需求要点**：一行一条。
7. **结论与改动**：表格「项 | 结论/决策（为什么） | commit」，一个改动一行。
8. **证据与验证**：要点式，保留关键数字与口径；明细给当日 `file/` 链接，不要贴原文。
9. **待验收 / 遗留待办**。
10. **总结与计划**：一两句话 + 后续待办（将成为下一个 job 的承接内容）。
11. **（可选）坑与经验**：只留会复用的，一行一条；写不下就进当日 `file/`。

简单任务（一次性上线、单日验收）用模板里的**简式**。

## 记录原则

- **当天事当天记**：每推进一段就落一条（更新「状态」清单即可），不要事后补。
- **证据留痕但要折叠**：结论要有依据，依据给**指针**（commit hash、`文件:行号`、命令要点、任务/工单 id、截图路径）；
  只有无法用指针表达的关键证据才写原文，且只写关键行。
- **待办闭环**：遗留项明确列出不丢失；承接上一 job 时先「进度回顾」（已完成/未完成分栏），再列本次待办。
- **核心信息优先**：job 只记录任务本身（做了什么、结论、证据要点、影响面）；临时产物一律进 `temp/`。
- **历史不回改**：已写好的「胖」job 不做回溯删改——细节在 git 历史里，删了反而丢信息。新记录一律按新规则写；
  只有本人明确要求时才做瘦身迁移（把细节搬进当日 `file/`，而不是删除）。
- **敏感信息不入库**：密码、密钥、内网凭据等不写入记录。

## 多设备记录

本工作记录可能在**不同的客户端设备**上编写/运行（多台电脑、笔记本等）。为方便日后回溯某些工作当时所处的环境，每个 job 头部设**设备行**：

```markdown
**设备**: MBLI（办公台式机）
```

- **标识写法**：机器名（Windows `hostname` / `$env:COMPUTERNAME`，Linux/Mac `hostname`）+ 括号内的人类可读说明（用途/位置），如 `DESKTOP-LAB01（实验室跑批机）`。
- **一个 job 内换设备**：本次推进中途换了设备（如从台式机换到笔记本继续），在设备行并列注明，运行记录条目中也可用时间戳标注所在设备。
- **环境信息**：设备行只是锚点；影响结论的环境细节（系统版本、引擎版本、依赖等）应写进运行记录本身，便于事后复现。

## 临时文件（temp 目录）

开发过程中的**临时产物默认全部进 `temp/`，不进 `work_record/`，也不入 git**（已在 `.gitignore` 忽略）。包括但不限于：

- 临时脚本（调试脚本、一次性查询/批处理脚本）
- 截图（验证截图、报错截图、屏幕录制）
- 视频、日志导出、中间数据、大文件

规则：

1. **目录结构**：`temp/` 下按与 `work_record/` 同构的日期目录存放——`temp/YYYYMM/YYYYMMDD/`，文件名可加日期前缀（如 `20260911_check.png`）。
2. **job 中引用**：提到临时文件时直接写路径（如 `temp/202609/20260911/check.png`），说明它是什么即可；正文不要依赖截图才能读懂，关键结论用文字落档。
3. **`file/` 放什么**（当日 `work_record/YYYYMM/YYYYMMDD/file/`，入 git）：
   - **二级文件（文字型细节/数据）**：常规操作，直接写、直接提交，**不需要**单独批准；
   - **附件（截图、录屏、大体积日志等二进制）**：仍须本人明确要求保留才整理进来；未经要求，`work_record/` 中不放这类文件。
   - 两类都**必须带 `jobN-` 前缀**（或日期前缀 + 被哪个 job 索引），确保能对号入座。
4. **定期清理**：`temp/` 不做版本管理，可随时清理；重要结论必须在清理前落进 job 或当日 `file/` 记录。

## todo.md 用法

记录不归属单个 job 的临时待办或长期事项，完成打勾，定期清理（已完结的移入对应 job 或删除）。条目尽量一行一条并附来源 job 链接。

## 对外模板仓库（GitHub）

GitHub 仓库 `limingboGitHub/work-record` 是**对外只读的「说明 + 模板」仓库**：只放 `README.md` 与
`work_record/_template/*`，**不放任何工作记录**（job 记录只在本库、只推 Gitee）。
README 或模板有改动后，跑一次同步：

```powershell
pwsh -File tools\sync-template-repo.ps1 -DryRun   # 先看会同步哪些文件（不推送）
pwsh -File tools\sync-template-repo.ps1           # 实际同步
```

脚本做法：从本库取上述文件 → 在 `temp/` 里生成一个**单提交的全新历史** → 强推覆盖 GitHub `main`。
因此远程历史里**永远不会残留工作记录**（2026-09-16 发现旧库历史混入了 7 个 job 文件，已清空重建）。

- 本库**不配置** `github` 远程，避免误把记录推上去；记录一律只推 Gitee。
- 旧库（含 7 个 job 文件的那段历史）仍有完整备份：本地 `D:\projects\work-record`。

## 归档

旧格式、零散的历史记录统一移入 `_legacy/`（按年分子目录），不与现行 `YYYYMM/YYYYMMDD` 结构混放。

## 日常操作

**绝大多数时候：不建新文件，往当前 job 追加。**

1. 推进过程中**只更新「状态」清单 + 结论表格**（新的需求/事项用 `## 追加（M/D HH:MM）：…` 起一节）。
2. 出现大块细节时复制 `_template/二级文件模板.md` 到当日 `file/jobN-<主题>.md`，正文只留摘要 + 链接。
3. 收尾：过一遍「job 自检清单」，`git add` 本 job（含当日 `file/` 里的二级文件）并提交，commit message 一行写完。
4. 临时脚本、截图、视频等放 `temp/YYYYMM/YYYYMMDD/`（不入 git）；确需入档的附件须经本人明确同意后放当日 `file/` 目录。

**仅当本人说「新建一个 job」时：**

5. 建目录 `work_record/YYYYMM/YYYYMMDD/`（当天第一个 job 时再建即可）。
6. **先确认当天最大 job 编号**（多会话共用编号）：`git pull` 或 `ls work_record/YYYYMM/YYYYMMDD/`，取 +1（**不要 `git add -A`**，避免提交别的会话未完成的 job）。
7. 复制 `work_record/_template/job模板.md` 为 `jobN.md`，填标题、关键词、设备；与前序工作有承接关系时写承接链接块和「进度回顾」。
