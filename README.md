# Work Record

按「月 → 天 → job」组织日常工作记录。本仓库只保留轻量级记录与关键信息。

## 目录结构

```text
work_record/                    # 工作记录（本仓库，git 管理）
├── README.md
├── job-template.md             # job 模板
└── 2026-09/                    # 以月为单位
    └── 2026-09-09/             # 以天为单位
        ├── job1.md             # 当天第 1 项工作
        ├── job2.md             # 当天第 2 项工作
        └── file/               # 当天与工作内容相关的图片、附件

# 以下两个目录与本仓库平行（同级），不纳入本仓库 git
../work_record_temp/            # 平行 temp：工作临时，按日期隔离
│   └── 2026-09/2026-09-09/     # 与记录库同日
│       ├── scripts/            # 当天临时脚本
│       ├── output/             # 当天中间输出、一次性产物
│       └── bigdata/            # 当天过程数据、可丢弃数据
../work_record_archive/         # 平行 archive：持久化大文件，按日期隔离
    └── 2026-09/2026-09-09/     # 与记录库同日，便于与 job 对齐
        ├── datasets/           # 需长期保留的数据集
        ├── artifacts/          # 模型、导出包、发布产物
        └── refs/               # 外部参考资料、镜像副本
```

temp 与 archive **同样使用 `YYYY-MM/YYYY-MM-DD/`**，与 `work_record` 日期一一对应：某天 job 产生的临时文件放 temp 同日，需长期保留的大文件放 archive 同日。

## 内容放置原则

本目录**尽量只放轻量级记录与关键信息**（Markdown 文档）。避免把临时脚本、一次性输出、大体积文件塞进仓库，保证 git 历史可追溯、仓库体积可控。

| 内容 | 放哪里 | 是否进 git |
|------|--------|------------|
| job 记录、结论、待办、索引 | `YYYY-MM/YYYY-MM-DD/jobN.md` | 是 |
| 工作相关的截图、说明图、小附件 | 当天目录下的 `file/`，如 `2026-09/2026-09-09/file/login-flow.png` | 是（注意体积） |
| 临时脚本、调试代码 | `../work_record_temp/YYYY-MM/YYYY-MM-DD/scripts/` | 否 |
| 中间输出、日志片段、一次性产物 | `../work_record_temp/YYYY-MM/YYYY-MM-DD/output/` | 否 |
| 过程中的大数据、可丢弃数据 | `../work_record_temp/YYYY-MM/YYYY-MM-DD/bigdata/` | 否 |
| **需长期保留的重要大文件**（数据集、模型、导出包等） | `../work_record_archive/YYYY-MM/YYYY-MM-DD/` 下按类型分子目录 | 否；本仓库只做**索引与追溯** |

三层分工（均按月/天对齐）：

- **`work_record`**：轻量记录 + 索引（进 git，长期可追溯）
- **`../work_record_temp/`**：工作临时区（随时可清）
- **`../work_record_archive/`**：持久化大文件存档（长期保留；job 里写路径索引）

- 当天 job 引用 `file/` 内附件时，在 job 中用相对路径，如 `./file/api-sequence.png`。
- 归档到 archive 后，在 job 中记录相对路径、用途与日期，例如：`../../../work_record_archive/2026-09/2026-09-09/datasets/export.csv`。
- `../work_record_temp/` 建议按日期清理；不要依赖它作为唯一存放点——重要结论仍应写回 job 记录。

## 使用方式

1. **建目录**：每月建 `YYYY-MM/`，每天在该月下建 `YYYY-MM-DD/`；需要附件时在该天下建 `file/`。
2. **建 job**：默认**续写当前 job**。只有明确说要新建 job（或明确表示上一件事已闭环、要另开一件）时，才创建下一个 `jobN.md`。进行中的过程、旁支动作都写进当前 job 的「进度记录」，不要自行拆分。
3. **填写**：按模板填写任务描述、待办、进度等；进度随做随记，不要攒到最后。模板保持精简，细节字段可在使用中按需补充。
4. **收尾**：完成或下班前勾完待办、更新「状态」、补「明日计划」。

## 什么算一个 job

**默认约定：未明确要求新建 job 时，一律视为仍在当前 job 中工作。**

| 规则 | 说明 |
|------|------|
| 续写优先 | 当天未明确要求新建时，中途插曲、次要问题、格式调整等都追加进当前 job 的「进度记录」 |
| 闭环再开 | 你认为当前目标已闭环、要另开一件独立事项时，明确提出「新建 job」或等价说法 |
| 明确才新建 | 未说新建 → 不新开文件；说了新建 → 创建下一个 `jobN.md` 并写清任务 |
| 跨天续做 | 某天没做完，隔天继续做同一件事：新建当天的 `jobN.md`，用「关联工作（文件索引）」串成概念上的同一个 job |

判断标准（简化）：

- 是否已经明确要求新建 job？**否** → 写进当前 job 的「进度记录」；**是** → 新开 `jobN.md`。
- 不再按「换了一件事做就自动拆文件」来判断，避免把同一段工作拆碎。

示例：

| 场景 | 做法 |
|------|------|
| 当前 job 做到一半，顺手改了几行配置 | 进度记录追加 |
| 同一目标下连续多轮调试 | 进度记录追加 |
| 明确说「这个 job 收尾，新建一个做 XX」 | 新建 `jobN.md` |
| 你认为已闭环并要求另开事项 | 新建 `jobN.md` |
| 今天未做完，明天继续做同一件事 | 明天新建 `jobN.md`，在「关联工作」中互指前后文件 |

## 关键字与关联索引

- **关键字**：在「基本信息」中用 `#标签` 填 3～8 个，便于全文检索与归类（如 `#登录` `#后端` `#缺陷修复`）。
- **关联工作（文件索引）**：把**概念上的同一个 job** 跨天串起来。典型场景：某天 job 没做完，后续某天又新建 `jobN.md` 继续做——文件上是多天多份，工作目标上仍是同一件事。双方在「关联工作」表中用相对路径互指，例如 `../../2026-08/2026-08-20/job3.md`。
- 路径以当前 job 文件所在目录为基准：`./` 同天、`../` 上一级日期目录、`../../` 回到月层后再进入其他月/天。
- 检索示例（在仓库根目录执行）：`rg "#登录" -g "*.md"` 或按文件名打开对应 `jobN.md`。

## job 状态约定

| 状态 | 含义 |
|------|------|
| 未开始 | 已建文件，尚未动手 |
| 进行中 | 当天正在推进 |
| 已完成 | 目标达成，细节已沉淀 |
| 已阻塞 | 卡住，写清原因和所需帮助 |
| 已取消 | 不再做，备注原因 |

## 命名建议

- 日期目录：`2026-09-09`（零填充，便于排序）
- job 文件：`job1.md`、`job2.md`……按当天创建顺序递增，不换描述性文件名
- 同一天多个 job 用独立文件，避免单文件过长
- 附件文件：放在 `file/` 下，名称可带简短语义（如 `diagram.png`、`error-log.txt`）

## Git 管理

- 本目录（`work_record`）使用 git 管理，便于按时间追溯记录变更。
- 只提交 Markdown 记录与确有必要的轻量附件；临时脚本、大数据、中间输出放在平行目录 `../work_record_temp/`，不纳入本仓库。
- 建议在完成一天记录或关键节点后 commit，提交信息可写 `记录 2026-09-09 工作` 或具体变更摘要。
